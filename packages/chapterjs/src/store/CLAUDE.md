# `store/`: what the bot keeps from one restart to the next

`export const warnings = store<Warning[]>({ scope?, storage?, expires? })`, from any file of `src/`. The name of the export is the name of the store (a default export takes the name of its file; two stores with the same name are reported, the later one left out, since they would share a file; a list is refused). `store()` is typed the same everywhere, so it is a normal export of `index.ts`. The core it is built on is described in `packages/chapterjs/CLAUDE.md`.

## `store.ts`: what the user holds

- `store<T>(config)` returns a `Store<T>`: `get`, `set`, `update` (read, change, keep in one go through `backend.update()`, so nothing written meanwhile is lost, in one process or several; `change` may run again and its result is checked with `checkJson()` each time; the expiration stays unless `options` give one), `increment(key, by = 1, options?)` (an `update()` adding to a number from 0; typed with `this: ScopedStore<number>`, so it is underlined on a store of anything else, and refused at runtime on a value that is not a number or a `by` that is not a finite number), `delete`, `getMany(keys)` (the backend's `get` for each, at once), `setMany([[key, value], …], options?)` (every key and value checked before anything is written, then the backend's `set` for each), `deleteAll(prefix?)` (the backend's `clear`, under the scope: a store per server only forgets the data of its server), `entries(prefix?)` (`StoreEntry<T>[]`: `key` without the scope, `value`, `expires: Date | null`), `ttl` (ms, `null` forever, `undefined` none) and `in(guild)` (the same store for one server: a `ScopedStore<T>`, everything but `in`).
- A key (`StoreKey`) is a text or a list of texts (`parts()` refuses an empty list, an empty text and anything that is not a text); `entries()` lists by prefix. The backend gets the full key: the scope first (`[guildId, ...key]` for a store per server, the key itself for a global one).
- A value is JSON: `checkJson()` refuses `undefined`, non-finite numbers, bigints, functions, symbols, and any object whose prototype is not `Object.prototype` or `null` (a `Date`, a `Map`, a class instance), naming the path (`the value.list[0].at is a Date`) and what to keep instead.
- Expiration: `expires` on the config (a `Duration`, 1 s at least) is the default of every `set()`; `set()`/`update()` take `{ expires: Duration | Date | null }`. The backend keeps `expiresAt` in ms; `Date.now()` is the clock of the store, the backend has its own `now` (tests mock both).
- `storage` (`StoreStorage`: `'file'`, the default, or `'redis'`) says which backend of the process keeps the data; the store object asks `storeBackend(storage, name)` on every call. Nothing of the framework writes to Redis but a store that says `'redis'`.
- The state behind `Symbol.for('chapterjs.store')` (`storeStateOf`) holds the config and, once the loader bound it (`bindStore`), the `name`, `scope`, `storage` and `expires`. Before that, every call throws "This store was not loaded by ChapterJS…": a store that is not exported refuses to serve, like a component. The store object keeps no data: the backend does, by name, so a reload (a new module, bound again to the same name) sees the same data.

## `scope.ts`: the server the code runs for

An `AsyncLocalStorage` of one object per run (`{ guildId }`): `withGuild(guildId, fn)`, `currentGuildId()` and `currentRun()` (that object: what tells one run of the files from another, for `waiting/`), plus what stores and rankings share about it: `scopeParts(what, name, scope, guildOf)` (the scope part of a key, or the message naming the kind) and `guildIdOf()` (what `in()` was given) (`null` for a function that runs for no server, `undefined` outside any function the framework runs). Set by the routers around every function they run: `runInteraction` (`guildId` in `RunOptions`, from `place.guild`), `EventRouter.emit` (the `guildOf` of the event), `TimerScheduler` (`null`). It follows the `await`s into the files the function imports. A store per server without a current server throws "`<name>` is a store per server, and this code does not run in one: use `<name>.in(guild)`…"; `in(guild)` overrides it.

## `backend.ts`, `file-backend.ts`, `redis-backend.ts`, `ipc-backend.ts`: where the data is

- `StoreBackend` (`get`, `set`, `delete`, `entries(prefix)`, `update(store, key, change)`, `clear(store, prefix)` → how many, `close`) over `StoreEntry { value, expiresAt }` and full keys. One backend per storage and per process: `setStoreBackend(storage, backend | null)` (called by `createProject` for every `StoreStorage` of `STORAGES`), `storeBackends()` lists them, `storeBackend(storage, name)` throws "Stores only work while the bot runs" when the process has none at all, and a `NowhereToKeepError` (`nowhereToKeep()`: "`<name>` is kept in Redis (storage: 'redis'), but REDIS_URL is not set…") when it has backends but none for that storage. `encodeKey` is `JSON.stringify(parts)`: unambiguous whatever the parts hold. `update()` reads and keeps with nothing written in between: its `change` (`StoreChange`) gets the current entry and returns the next one, or `undefined` to write nothing, and may run more than once. `KeyQueue` runs the updates of one key one after the other in a process (chained with `await`, so an error keeps the line of the file that asked), so only processes compete for a key; after `UPDATE_ATTEMPTS` (50) failed tries, `tooBusy()` explains it.
- `FileStoreBackend(dir)`: the default, `data/` of the project (`DATA_FOLDER`), one `<name>.json` per store (`{ version: 1, entries: [[key, value, expiresAt], …] }`), loaded on first use (a file it did not write is an error naming it; a name a file can't be called is refused), kept in memory, written after `writeDelay` (100 ms, one write per burst) atomically (`<file>.<pid>.tmp` then rename) and on `process.on('exit')` (synchronous), expired entries dropped when read, when asked for, and by a sweep every `sweepEvery` (60 s, unref'd). `update()` and `clear()` read and write without an await in between: atomic in its process by construction. `close()` writes what is pending and stops the sweep.
- `RedisStoreBackend(client, { prefix?, scanCount?, now? })`: the backend of the stores with `storage: 'redis'`, on the `RedisClient` of `src/redis/` (described in `packages/chapterjs/CLAUDE.md`). One Redis key per value, `<prefix><store>:<part>:<part>` (`escapePart`: `%`, `:`, `*`, `?`, `[`, `]` and `\` of a part become `%XX`, so `:` separates and a `SCAN MATCH` pattern is safe), the value as JSON, the expiration given to Redis with `SET … PX` (a value already expired is a `DEL`) and read back with `PTTL` (`-1`: forever, `-2`: gone). `update()` is a transaction on a connection of its own, lent from a pool (`transactions`, 4 at most besides the main one, opened with `connect`, by default a `RedisClient` on the same address; WATCH and MULTI belong to a connection and the main one carries every other command): `WATCH`, `GET` + `PTTL`, `change`, then `MULTI`, `SET`/`DEL`, `EXEC`; a `null` EXEC means someone wrote the key since WATCH, and it runs again; a `change` that throws or writes nothing is followed by `UNWATCH`, and the connection is always given back. `clear()` is the SCAN of `entries()` then one `DEL` per batch. `entries(prefix)` is a `SCAN MATCH <key>*` (`<store>:*` for an empty prefix) in pages of `scanCount` (500), the keys checked part by part after (`a:b*` also matches `a:bc`), then `MGET` plus one `PTTL` per key, pipelined. `prefix` is `DEV_PREFIX` (`dev:`) under `chapterjs dev` and nothing in production, so one Redis never mixes the two. `client` is exposed for the preflight `ping()`; `close()` closes it. Nothing is written that a store did not ask for: no `FLUSH`, no key of the framework.
- `ranking-backend.ts`: where the scores of a ranking (`src/ranking/`) are kept. `RankingBackend` (`add`, `set`, `score`, `rank` from 0 in an order, `range(order, start, count)`, `remove`, `size`, `clear`) over a name and a scope. `StoreRankingBackend(storeBackend)` keeps them in any backend of stores, one entry per member (`[...scope, id]` → score; `add` is its `update()`, `top`/`rank`/`size` sort the entries of the scope with `compareRanked`): files, the first process of a cluster and memory need no code of their own. A backend with a native way gives it with the optional `rankings()` of `StoreBackend`; `rankingsOf(backend)` picks it, else a `StoreRankingBackend` kept per backend.
- `redis-ranking.ts`: `RedisRankingBackend`, what `RedisStoreBackend.rankings()` gives: one sorted set per scope, its key the key of the scope (`<prefix><name>:<server id>`, `<prefix><name>` for a global one), `ZINCRBY`, `ZADD`, `ZSCORE`, `ZREVRANK`/`ZRANK`, `ZREVRANGE`/`ZRANGE … WITHSCORES`, `ZREM`, `ZCARD`, and `ZCARD` then `DEL` for `clear`.
- `MemoryStoreBackend()`: the data in memory and nowhere else, with `reset()` to forget everything: what `chapterjs test` gives the project for every storage (so a store kept in Redis needs none), and what `chapterjs build` gives it (the files run once and keep nothing), so a test or a build never touches `data/` and every scenario starts from nothing.
- `IpcStoreBackend(channel)`: the backend of a process started by another: every call is a `StoreRequest` (`{ type: 'store', id, op, store, key | prefix, entry? }`) sent on the channel, answered by a `StoreReply` (`{ type: 'store', id, result | error }`). `update()` can't send its change over the channel: it reads with `get`, runs the change in the worker and asks `swap` (`expected` entry, or `null`, and the new `entry`), which the first process keeps only if the entry is still the expected one (same JSON), inside its own `backend.update()`; otherwise it runs again. `clear` is one request. `serveStores(backend, reply)` is what the first process runs on each message of a child: `cli/cluster.ts` registers it per worker, so the coordinator's `FileStoreBackend` is the one home of the data; `cli/start.ts` gives a worker the IPC backend (`stores` of `createProject`) and the coordinator passes its backend to `runCluster` (`stores`). `Channel<Out, In>` is the two ends as a process and a fork have them, so tests join two emitters.

## `declaration.ts` and the wiring

- The `Declaration` of stores: `read` checks the keys (`scope`, `storage`, `expires`), the scope, the storage (`STORAGES`), the expiration (`DURATION_EXAMPLE`, 1 s at least) and that the name can name a file (`[\w.-]+`), then binds the store → `LoadedStore { name, scope, storage, expires }`.
- `cli/project.ts` loads it with the others (`sameNames(…, 'store')` for duplicates), leaves out with a `NowhereToKeepError` a store whose storage the process has no backend for (a Redis store without `REDIS_URL`: reported like a duplicate, and the store says the same when used), counts it in `summary` ("2 stores"), creates the backends (`options.stores` by storage, else the file one on `data/` and nothing for Redis) and exposes `storeBackends`, `redisStores()` (the sorted names of the stores kept in Redis) and `closeStores()`, which `dev` and `start` await when stopping. `cli/redis.ts` is what `dev` and `start` share about Redis: `redisStores(address, log, { prefix })` (the backend, its outages logged with `⚠` once and `↻` when back), `checkRedis()` (a `PING` before Discord is reached, only when `redisStores()` is not empty: a Redis that does not answer is an error now, with its reason) and `describeRedisStores()` (the `ℹ The store sessions is kept in Redis at host:port` line, printed after the summary, and again in `dev` when the list changes on a reload). `start` gives every process its own Redis backend (it is made to be shared; only `file` goes through IPC), and a load that fails only because of `NowhereToKeepError`s ends with "Give REDIS_URL to the bot the way your host does it…" instead of "run chapterjs build again". `data/` is in the `_gitignore` of every template, which also show `REDIS_URL` and `REDIS_PASSWORD` commented in `.env.example`.
- Not written yet: another backend (a database) is an implementation of `StoreBackend`, a value of `StoreStorage` and a backend given to `createProject`; `scope: 'user'`; `onExpire`; moving the data of a store from one storage to another (on purpose: nothing is written to Redis but what a store asks).
