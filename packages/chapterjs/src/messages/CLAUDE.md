# `messages/`: every text the bot answers with, one declaration per language

`export default language({ locale, default?, texts, commands?, framework? })`, from any file of `src/` (the template keeps `src/messages/en-US.ts` and `fr.ts`).

- `locale` is the language (one of the `Locale` of `discord/types/common.ts`, refused when the file loads otherwise).
- `texts` its texts by key; `default: true` marks the language used when the one asked is not there (exactly one, unless there is only one); `commands` what Discord shows of the commands in that language; `framework` its translations of the framework's phrases.
- Every handler (commands, components, modals, events, tasks) then receives `t`: `t('welcome', { name })`, `t.locale`, and for another language `t.in('fr', 'welcome', { name })` (or `t.in('fr')`, the same `t` for it).
- Not written yet: a language set per server, the framework's phrases where the gender of `{what}` matters (a language writes a neutral phrase).

## `messages.ts`: `language()` and the types

- `language()` is a `const` generic so the texts keep their literal types. `LanguageConfig<T, L>` has its `default` typed `false` when `L` is a key of `ProjectLanguageDefaults`: how a second `default: true` is underlined in both files once the generated types know them. `LanguageDeclaration` is the branded result.
- `MessageText`: a string, or a `PluralText` (one form per quantity among `zero`/`one`/`two`/`few`/`many`/`other`, `other` required, picked by a `count` that must be a number).
- `FrameworkTexts`: the phrases the bot answers by itself, with the words `command`/`button`/`menu`/`form` that `{what}` stands for; `needsPermissions` is a plural.
- `Placeholders<T>` / `ParamsOf<T>` / `ParamsArgs<T>`: the params of a text from its placeholders, at type level, read left to right like the runtime (`{{` and `}}` are braces written as is; a plural adds `count`; a wide `string` takes an optional record).
- `Translator<M>`: `in()` has two forms, `in(locale, key, params)` gives one text, `in(locale)` the `t` of that language. Its `locale` is typed `LocaleGiven<L>` with `L extends ProjectLocale | (string & {})`: the editor offers only the languages of the project (`ProjectLocales`, an interface the generated types augment with one key per language declared, `ProjectLocale` its keys), while any `Locale` of Discord is accepted (`interaction.locale`, `guild.preferredLocale`: `t` takes the closest one declared), a word that is no language of Discord is underlined with the project's, and a plain `string` is refused. Tested against the real language server in `test/editor.test.ts`.
- `ProjectMessages`: an empty interface the generated types augment. `MessagesOf<F>`: the texts of a language declaration. `TranslationContext`: `{ t }` when `ProjectMessages` has keys, `{}` otherwise (`t` does not exist, in types nor at runtime, for a project without a language).

## `translate.ts`: the runtime

- `compile()`: a text cut once around its placeholders, by a left-to-right scanner (`{{`/`}}` are literal braces, a `{` with another `{` before its `}` too). `compilePlural()` / `templateOf()`: a `PluralTemplate` has its forms and `count` first in its params.
- `pickLocale()`: the language asked → the same one → one of the same language in another region (`en-GB` → `en-US`, `es-419` → `es-ES`, `zh-TW` → `zh-CN`) → the default.
- `fill(key, template, params, locale)`: a missing param is a `TypeError` naming it and showing the call to write; a number is written with `Intl.NumberFormat` of the language, a plural picks its form with `Intl.PluralRules`, both cached per locale, `other` when the form is missing.
- `translatorFor()`: **one `Translator` per (messages, locale asked), cached in a `WeakMap`**, so a dispatch allocates nothing; `missingTranslator()` is cached per locale too. It answers with the default language's text, written its way, when the picked language has none.
- `translation(ctx, locale)`: what a router spreads into a context (`{ t }` or `{}`). `translatorOf(ctx, audience)`: a `t` for what the bot sends, which only says the language is missing when called without one.
- **`audienceLocale()`: `t` speaks the language of those who will read what is sent**, because a message is sent once for everyone: the person when they alone see it (an `ephemeral` answer, known from the command or component file before `run`, or a component of a message that is itself ephemeral, or a private message, or a modal), else the server's `preferred_locale` when it is a Community server (`features` has `COMMUNITY`: elsewhere Discord always says `en-US`), else `null` = the default language. `ready` and tasks get the default.
- The routers read `Context.messages`: `audienceLocale` with the person (`raw.locale`), the place and the `ephemeral` of the file for an interaction; `localeOf()` in `events/router.ts` for an event (the server, member, channel, role or message the context carries, from the `guildOf` of its registry entry).

## `phrases.ts`: the framework's own phrases

- `FRAMEWORK_TEXTS` (the English of every phrase), `FRAMEWORK` (compiled), `phrase(ctx, locale, key, { what, permissions, count })`: the phrase from the language file picked for `locale` when it translates it, else the English one, `{what}` translated the same way.
- `interactions/dispatch.ts` wraps it as `says(interaction, key, params)` and `refuse(interaction, key, params)` (the language of the person: `interaction.locale`); `resolvePlace` returns a key (`guildOnly`/`dmOnly`/`notHere`) and the routers add `what`.
- No phrase is written in a router: a new one is an entry of `FrameworkTexts` and `FRAMEWORK_TEXTS`, plus its row in the reference.

## `declaration.ts`: loading and assembling languages

- The `Declaration` of languages. `read` validates one declaration: `locale`, `default`, `texts` with their placeholders (a plural: known forms, `other` present, each form a text), `framework` (known keys, each with exactly the placeholders of the English phrase), the shape of `commands`; no length limit is invented → `LoadedLanguage`.
- `assembleMessages(entries)` puts the languages together → `LoadedMessages` (`default`, `locales` compiled, `commands` and `files` by locale):
  - **A language may be declared in several places** (the texts of a feature next to it), merged by locale (texts, `framework`, `commands`; the same key twice is reported on the later declaration, the first wins; `default: true` in any of them decides for the whole language; `files` keeps the first). One default (the errors name the declarations, `siteName`).
  - **`t` is typed from every declaration, the default language first.** A text the default language does not have is taken into it from the language that has it (`en-US` first, then the others in order: a module written in other languages than the project's default still works, and `translateCommand` describes a command the same way when the default language does not).
  - Another language may have only some of the texts. Every language that has a text takes the placeholders of the language it comes from (the union of the forms for a plural, so a plural in one language may be a text in another); a language that differs is reported on its declaration and left out, the others still work.
- `messagesDeclarations(languages, defaultLocale?)`: the augmentation `interface ProjectMessages extends MergedMessages<[MessagesOf<typeof import('../../src/<file>')<.export>>, …]> {}` over every declaration, the default language first (the first language, by file then export, until it is known), then `en-US`, then the others: the first declaration wins for a key several have, as the bot does, so the editor types `t` from the language itself, on every keystroke, with nothing generated from its content. Plus `interface ProjectLocales { 'en-US': true; 'fr': true }` from the locales declared (what `t.in()` offers).
- `languageDefaultsDeclaration(defaults)`: `interface ProjectLanguageDefaults { 'fr': true; 'en-US': true }` when more than one language says `default: true` (`defaults`: the locales that say it now, `TypesInfo.languageDefaults`, counted before a declaration is put back to its last good version, so that both are underlined; `sync` knows none), which `LanguageConfig` turns into a type error on each `default: true`, so a second default is underlined in the editor and not only reported in the console.
- Which language is the default is known once the files ran: `writeTypes(cwd, project.typesInfo())` (`dev` after every load, `build` once the files ran); `sync` reads the files instead (`scanLanguages()`: `language({ locale: '...' })` and `default: true` found by text, the first one typing `t` otherwise).

## `commands.ts`: the texts of commands

What Discord shows of a command (name, description, options, choices) is registered, not sent by the bot, so it is the one thing translated by data: the `commands` of a language, by the name of the command (`'ping'`, `'mod ban'`), in the shape of the `locales` of a command.

- **A command has its texts in one place, and `description` in its file decides which.** With it, the file owns its texts (`locales` included: `LoadedCommand.described`) and a language file that mentions the command is an error on that language file. Without it, `locales` is refused in the declaration, `description` (and an option's) is left empty, and `translateCommand(site, command, messages)` fills them from the default language (its `commands.<name>.description`, `options.<name>.description`; what is missing is an error on the command saying where to write it, and the command is left out) and takes the other languages as translations, each checked with the same `checkLocales` as a command (exported from `commands/declaration.ts`), an error naming its file (`failed`).
- `unknownCommands()` names the commands no declaration has, with the file. Registration follows by itself: the merged command changes the payload hash.
- The editor offers the command names, and only the ones a language may translate: `commandsDeclarations(commands)` writes `interface ProjectCommands { 'ping': true, 'mod ban': false }` to `types/project.d.ts` (`true` when the language files describe it, `false` when the command has its own `description`), and `CommandsTranslations` maps the `true` ones to a `CommandTranslation` per name, any name when the project has no command, and no name at all when every command is described. Both come from running the files (`project.typesInfo()`); `sync` runs nothing, finds the names by reading the files (`scanCommands()`) and offers them all; the runtime refusal stays for the save made between two reloads.
- The command files are never referred to from there: their `t` is typed from the languages, and a language's `commands` typed from the command files would be a circle (TS7022); options and choices are checked when the files load.
- `cli/project.ts` runs `translateCommand` on every command once the languages are assembled (a command that can't be described is removed), keeps the last good version of each language declaration (like events), assembles them on every load (a language that stops matching the others keeps its last version that did), sets `Context.messages` on connect and on every reload so a saved text is used at once.

## The texts of components: `DynamicText`

- A text of a component (`components/component.ts`) is a string, or `({ t, data }) => string` (`TextContext`) run when the message is sent, for who will read it: a button's `label`, a menu's `placeholder` and the `label`/`description` of its options (`RichOption`), a form's `title` and the `label`/`description`/`placeholder`/`content` of its fields.
- A piece made from one is deferred: `Rendered.raw` is a value or a function of `t` (`Deferred`, `resolve()`, and `compose()` for rows, sections, containers and `autoRows`), and `buildMessage(input, { t })` resolves it: every sender gives the `t` of its audience (`interaction.reply` with the `ephemeral` of the call, `edit`, `followUp`, `update`, `showModal` with the person, `sendMessage` and `createPost` with the server, `message.edit`, `webhook.send`).
- A written text is checked when the file loads, a function's result when the message is sent (`resolveText`, `checkDynamicText`). Embeds need none of this: an embed file is already a function of what it shows, `t` included.
- `t` is given to a handler before it runs, for the audience its file declares (`ephemeral` of the file, which is also the default of its answers, so the call repeats nothing): an answer made private at the call keeps the language of the server in its `content` while its components are computed for the person. Documented as a warning, not solved: a string is already resolved. The components of that answer are fine: they are on an ephemeral message.
