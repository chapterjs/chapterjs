# `waiting/`: waiting for what comes next

`await channel.waitForMessage({ from?, matches?, within? })`, `channel.collectMessages({ ...same, max? })`, `message.waitForClick({ from?, within? })` and `message.waitForReaction({ from?, emoji?, within? })`, from any function of the files (a command, an event, a component, a task). Methods of structures, not declarations: what is waited for only exists while a function runs. Each resolves with what came, or `null` (`[]` for a collect) when `within` passed (one minute by default, 1 s to 1 day). A restart or a stop ends every wait with what it has.

## `waiters.ts`: one mechanism for every kind

- `Waiters` (interface) and `MemoryWaiters` (the default, in the process): `wait<T>({ kind, match, max, within })` → what was taken, in order; `wants(kind)` (so the bot builds nothing when nobody waits); `offer(kind, offered)` → whether a wait took it; `close()`. `WaitKind` is `message | reaction | click`; a new kind is a kind and the place that offers it.
- A message or a reaction goes to every wait that wants it, and the events still run; a click goes to one wait only (`EXCLUSIVE`), and the `run` of the component does not run.
- A `match` that throws (a `matches` function of the files) ends its wait with that error, thrown where the files await: reported with their line like any error of theirs.
- Waits never keep the process up (unref'd timers). Everything of one server reaches one process (its shard), so in-memory waits always hear what they wait for; a backend shared between machines would be another `Waiters`.
- `WaitWatcher` (`parked(run)` / `resumed(run)`, once per run of the files whatever its number of waits) is how `chapterjs test` knows a run is waiting for the test to act: a run is the object `withGuild()` creates for each function the framework runs (`store/scope.ts`, `currentRun()`).

## Where it plugs in

- `structures/wait.ts`: the options and what they become (`readWithin`, `personId`, `readMatches`: a text compared whatever the capitals and the spaces around, a `RegExp` tested from the start, or a function where only `true` counts; `readEmoji`: the emoji itself, a custom one by name, id or `<:name:id>`), the public types (`WaitForMessageOptions`, `CollectMessagesOptions`, `WaitForClickOptions`, `WaitForReactionOptions`, `PersonInput`, `Click`, `WaitedReaction`) and `waitFor()`, which the methods of `channel.ts` (in `TextBasedMethods`) and `message.ts` use. Without `from`, a message or a reaction of a bot never counts.
- `Context.waiters`, made by `createBot()` (`options.waiters`, a `MemoryWaiters` by default; `cli/project.ts` gives one with the `waits` of its `ProjectObserver`), closed by `bot.close()`. `core/bot.ts` offers `MESSAGE_CREATE` (a `Message`) and `MESSAGE_REACTION_ADD` (`offerReaction()`: who reacted is the member Discord sends, else the user the bot knows, else Get User) after the cache, before the events.
- `components/router.ts` offers a click once the component is found and checked (data, `where`, `who`), with the same values its `run` would get (`OfferedClick`: `interaction`, `user`, `member`, `name`, `data`, `values`, `is(component)` by kind and bound name). A click taken is answered by the files; after 2 s without an answer the router sends `deferUpdate()` so the person never sees "This interaction failed". `run` is optional on `button()` and `select()`: one only waited for answers "not available any more" once nothing waits, and the smoke check of `chapterjs test` leaves it out.
- `usage.ts`: `MESSAGES_USE` (`.waitForMessage(` / `.collectMessages(` → `GUILD_MESSAGES`, `DIRECT_MESSAGES`, `MESSAGE_CONTENT`) and `REACTIONS_USE` (`.waitForReaction(` → the reaction intents), `CodeUse`s of `loader/usage.ts`, so the intents follow the code like those of events, the files are named by the preflight for a privileged one, and `build.json` keeps them (`uses`). A click needs no intent.
- `chapterjs test`: `Observer.settle()` waits for everything the files started except the runs that wait (`#parked`), waking up each time one promise ends or a run parks or resumes; `bot.endWaits()` ends every wait as if its time was up (time does not pass in the test server). A button or a menu found on a message (`reply.button('Yes')`) is clicked on that message (`FOUND_ON`), as a person would.
