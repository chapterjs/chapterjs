---
title: 'chapterjs start'
description: 'Run your bot for everyone, in production'
---

`chapterjs start` runs your bot on every server it is in. It is what the `start` script of your project runs, on the machine that hosts your bot:

<CodeGroup>
```bash pnpm
pnpm start
```

```bash npm
npm run start
```

```bash yarn
yarn start
```

```bash bun
bun start
```
</CodeGroup>

```text
✓ Commands updated for everyone
✓ Online as my-bot in 128 servers
ℹ Intents computed from your files: GUILDS, GUILD_MESSAGES, MESSAGE_CONTENT
✓ 4 commands, 6 events loaded
```

There is nothing to build first: your files run as you wrote them.

## What changes from dev

| | `chapterjs dev` | `chapterjs start` |
| --- | --- | --- |
| Servers | Your test server only | Every server, except your test server |
| Private messages | Never | Yes |
| Commands | Shown in your test server, at once | Shown everywhere |
| A file that can't run | Keeps its last working version | The bot does not start |
| Saving a file | Reloads it | Nothing: start the bot again |
| Something to fix on Discord | Waits for you | Stops and says what to fix |

## What it needs

One value: the token of your bot.

```bash .env
BOT_TOKEN=
```

On a host, you usually don't upload a `.env` file: you give `BOT_TOKEN` in its settings (often called "environment variables" or "secrets"). Both work, and the host wins when both are there.

<Warning>
  Your token is a password. Never put it in your code, and never commit your `.env` file.
</Warning>

## Your test server stays yours

Add `DEV_GUILD_ID` next to `BOT_TOKEN` in production too, with the same value as on your computer:

```bash .env
BOT_TOKEN=
DEV_GUILD_ID=
```

Production then leaves that server alone, and you can keep working with `chapterjs dev` on the **same bot** while it is online for everyone:

- what happens in your test server is only handled by `chapterjs dev`;
- what happens everywhere else, and in private messages, is only handled by `chapterjs start`.

They never answer the same thing. Without `DEV_GUILD_ID`, production runs every server, your test server included.

### Commands are shown once

Your test server gets the commands of everyone, like any server. `chapterjs dev` does not give them a second time: it only adds the commands that are **new or different** in your project. Used in your test server, a command always runs the code on your computer.

While you are changing a command that is already in production, your test server shows it twice (yours, and the one everyone has), and `chapterjs dev` tells you:

```text
ℹ /poll is not the same here as in production, so My Server shows it twice: yours, and the one everyone has. It is shown once again when production runs your version.
```

Discord gives no way to hide one of the two. To never see that, use a second bot for development: another application in the Developer Portal, and its token in the `.env` of your computer.

## A file that can't run stops the start

In production, a bot with a broken command is worse than no bot. Every file is checked first, and nothing is sent to Discord if one fails:

```text
✗ src/commands/ban.ts This file has no default export. It should look like: import { command } from 'chapterjs'; export default command({ description: '...', run({ interaction }) { ... } })
✗ This file can't run, so the bot was not started. Fix it and start again: chapterjs dev shows the same errors while you write.
```

Run the `typecheck` script of your project before putting a new version online: it finds most mistakes without starting anything.

## Large bots

Discord splits large bots in several connections, called shards. ChapterJS asks Discord how many are needed and opens them by itself.

When there are many, it also spreads them over **several processes**, so your bot uses every CPU of the machine. You see it in the first line:

```text
✓ Online as my-bot in 18420 servers (20 shards, 5 processes)
```

Each process runs your project for its share of the servers, and what it prints starts with its number:

```text
[3] ✗ src/commands/poll.ts:8 Missing Permissions
```

- **Nothing to configure.** One process is used for every 4 shards, never more than your machine has CPUs. A bot under a few thousand servers runs in one process, like before.
- **A process that stops is started again**, and its servers are back in a moment. The others don't notice.
- **Stopping the bot stops them all**, cleanly.

To choose yourself, pass the number:

<CodeGroup>
```bash pnpm
pnpm start --processes 8
```

```bash npm
npm run start -- --processes 8
```

```bash yarn
yarn start --processes 8
```

```bash bun
bun start --processes 8
```
</CodeGroup>

### What it means for your code

Each process has its own memory. A variable of one process is not seen by the others:

```ts
// One counter per process: with 5 processes, 5 different numbers.
let commandsUsed = 0;
```

- The `ready` event runs once in each process, with the servers of that process.
- `guilds` and everything your bot [remembers](/memory) are the ones of the process.
- Private messages are all handled by the first process.

To share something between processes, keep it outside of them, in a database.

<Note>
  Every process runs on the same machine. Spreading a bot over several machines is not available yet.
</Note>

## Stopping

Press `Ctrl+C`, or let your host stop the process. The bot disconnects properly and goes offline at once:

```text
✓ Disconnected
```
