<Note>
  Comment écrire un fichier d’événement est dans [Événements](/fr/events) ; les événements sur les messages et leurs options dans [Messages](/fr/events/messages) ; `event()` et ses types dans [event()](/fr/reference/event).
</Note>

Un événement est le `name` d’une déclaration `event()`. Chaque section ci-dessous est un événement : quand ses déclarations tournent, les intents dont Discord a besoin pour lui (déduits de vos fichiers, jamais écrits par vous), ses options, ce dont le bot se souvient pour lui au-delà de [la valeur par défaut](/fr/memory), et ce que reçoit votre fonction.

Les intents sont nommés comme les affiche `chapterjs dev`. Trois sont privilégiés, à activer dans le [Developer Portal](/fr/setup/discord-application) : `GUILD_MEMBERS` est le Server Members Intent, `GUILD_PRESENCES` le Presence Intent, `MESSAGE_CONTENT` le Message Content Intent.

## Ce que donne chaque événement

Ce que reçoit votre fonction, événement par événement : ce dont parle l’événement, et le serveur où il s’est produit (`guild`). Chaque événement reçoit aussi `t`, dans la langue de ce serveur, quand le projet a une langue. Le type après deux-points est celui de cet objet, détaillé dans la section de l’événement ; `where: 'dm'` et `where: 'both'` affinent `guild` comme chaque section le dit.

## ready

| | |
| --- | --- |
| Quand | Le bot est connecté et connaît chaque serveur où il se trouve. Une fois par démarrage, jamais à nouveau lors d’un rechargement. |
| Intents | Aucun |
| Options | Aucune |
| Mémoire | Par défaut |

Chaque événement reçoit aussi `t`, dans la langue du serveur où il s’est produit, quand le projet a une langue : voir [`TranslationContext`](/fr/reference/messages#translationcontext).

<ResponseField name="user" type="User" required>
  Le bot lui-même.
</ResponseField>
<ResponseField name="guilds" type="ReadonlyMap<Snowflake, Guild>" required>
  Les serveurs où se trouve le bot.
</ResponseField>

## messageCreate

| | |
| --- | --- |
| Quand | Un message a été envoyé, sur un serveur ou en privé. Par défaut, seulement par une personne, sur un serveur. |
| Intents | `MESSAGE_CONTENT` (privilégié), plus `GUILD_MESSAGES` pour un fichier qui écoute sur les serveurs et `DIRECT_MESSAGES` pour un fichier qui écoute en messages privés |
| Options | `bots`, `where` ([MessageEventOptions](/fr/reference/event#messageeventoptions)) |
| Mémoire | Par défaut |

<ResponseField name="message" type="MemberMessage" required>
  Le message qui a été envoyé. Le type suit les options du fichier : `MemberMessage` par défaut, `GuildMessage` avec `bots: true`, `DmMessage` avec `where: 'dm'`, `MemberMessage | PrivateMessage` avec `where: 'both'` (`GuildMessage | PrivateMessage` avec les deux options). Les quatre sont dans [Message](/fr/reference/message#types).
</ResponseField>
<ResponseField name="guild" type="Guild" required>
  Le serveur. Avec `where: 'dm'` il n’existe pas ; avec `where: 'both'` il vaut `null` pour un message privé.
</ResponseField>

## messageDelete

| | |
| --- | --- |
| Quand | Un message a été supprimé. Par défaut, seulement sur un serveur. Des messages supprimés ensemble (par un modérateur, ou par `bulkDelete()`) font un `messageDelete` chacun. |
| Intents | `GUILD_MESSAGES` pour un fichier qui écoute sur les serveurs, `DIRECT_MESSAGES` pour un fichier qui écoute en messages privés |
| Options | `where` ([WhereEventOptions](/fr/reference/event#whereeventoptions)) |
| Mémoire | Par défaut : aucun message, donc `message.before` est `null` aujourd’hui |

Ce que reçoit un fichier sans `where` :

<ResponseField name="message" type="DeletedMessage" required>
  Le message qui a été supprimé.
  <Expandable title="propriétés">
    <ResponseField name="id" type="Snowflake" required>
      L’identifiant du message supprimé.
    </ResponseField>
    <ResponseField name="channelId" type="Snowflake" required>
      L’identifiant du salon où était le message.
    </ResponseField>
    <ResponseField name="channel" type="GuildTextBasedChannel" required>
      Le salon où était le message.
    </ResponseField>
    <ResponseField name="guildId" type="Snowflake" required>
      L’identifiant du serveur.
    </ResponseField>
    <ResponseField name="before" type="GuildMessage | null" required>
      Le message tel qu’il était, quand le bot s’en souvenait.
    </ResponseField>
  </Expandable>
</ResponseField>
<ResponseField name="guild" type="Guild" required>
  Le serveur où était le message.
</ResponseField>

Avec `where: 'dm'`, `guild` n’existe pas, et dans `message` `channel` est un `DMChannel | null` (la conversation privée, quand le bot la connaît), `before` un `DmMessage | null` et `guildId` n’existe pas. Avec `where: 'both'`, ce qui est privé arrive avec `guild: null`, donc `guild` distingue les deux.

Avec `where: 'dm'`, `guild` n’existe pas, et dans `typing` `channel` est un `DMChannel | null` (la conversation privée, quand le bot la connaît), et `guildId` et `member` n’existent pas ; avec `'both'`, quelqu’un qui écrit en privé a `guildId: null` et `member: null`. Avec `where: 'both'`, ce qui est privé arrive avec `guild: null`, donc `guild` distingue les deux.

## Quand Discord ne donne qu’un identifiant

Certains événements n’arrivent qu’avec l’identifiant de la personne : retirer une réaction, voter, écrire en privé, s’intéresser à un événement programmé. Quand le bot ne connaît pas encore cette personne, il la demande une fois à Discord avant de lancer vos fichiers, puis s’en souvient : `user` est toujours là. Comme pour [un salon que le bot ne connaît pas](/fr/events/messages#un-salon-que-le-bot-ne-connaît-pas), quand Discord refuse, l’événement n’est pas livré et on vous le dit :

```text
⚠ A reactionRemove event was not given to your files: Discord did not let the bot read the user who did it (Discord refused GET /users/{user.id}: Unknown User (10013)).
```
